# 선택 설계 → AWS 배포 연결 검증

기존 실측 후 발견된 제품 연결 누락을 보완했다. 엔진은 architecture_plan_id로
최신 선택·프로젝트 소유권·분석 근거·지원 스택을 재검증하고 카탈로그 스냅샷을 배포 기록에 남긴다.
클라이언트가 임의 CPU/메모리/최대 태스크 수를 지정할 수 없다.

웹의 선택 구성 배포 버튼과 AWS를 포함한 Action에서 ID를 전달한다. 어댑터는 small/medium/large에
대응하는 CPU·메모리·태스크·앱 AZ·DB MultiAZ·CPU 자동 확장 정책을 적용한다. 앱 준비 전 게이트는
닫히고, 실제 태스크의 AZ 배치와 건강 상태를 확인한다. 배포 준비와 중지 시 기존 자동 확장
등록을 제거한다. DB 변경은 실패 시에도 자동 복구하지 않으며 DB·기반 자원은 유지된다.

## 검증 구분

- 엔진 자동 테스트: 실제 FastAPI 등록→설계 생성→선택→배포 요청→AWS 어댑터 경계까지 검증.
- AWS SDK 대역 테스트: 세 규모별 task definition·ECS subnet/desiredCount·RDS MultiAZ 변경·스키마 초기화·확장 정책·중지 순서 검증.
- 거절 검증: 다른 프로젝트/미선택/오래된 계획, 직접 replica override, 알 수 없는 자원 필드, 부족한 AZ.
- 웹 lint·TypeScript·production build 검증.
- **2026-10-09 새 제품 경로로 medium 실제 AWS 배포를 검증했다.** 아래 실측 결과와 이전 Provider 직접 호출 실측을 구분한다.
- 이전 보고서의 자동 축소 미확인 결과는 그대로 유효하다. 정책 생성 코드가 있다는 것이 실측 성공은 아니다.

## 운영 전제

기반 스택을 준비하는 기존 provision 절차는 유지한다. 빈 AWS 계정 온보딩이나 모든 프로젝트의
자동 인프라 생성은 이 변경의 범위가 아니다. 갱신된 foundation.yaml과 출력 기반 설정의
DbInstanceId·세 AZ 서브넷 및 새 권한이 필요하다(기존 두 AZ는 small/medium만 지원).
현재 실제 앱 실행 범위는 Spring/PostgreSQL 샘플이다. 프리셋은 처리량 보장이 아니다.

## 선택 구성 실제 배포 실측 (2026-10-09)

`infra/aws/experiments/plan-deployment-check.py`로 폐기용 기반 스택을 만든 뒤, 실제 FastAPI
설계 생성 → medium 선택 → `architecture_plan_id` 배포 요청 → 실제 엔진 이미지 빌드/ECR 게시
→ AWS 어댑터 → 실제 AWS 자원까지 연결했다. FastAPI는 TestClient로 실행했으며
AWS 경계를 대역으로 교체하지 않았다. 브라우저 클릭 E2E는 아니다.

- 엔진 최종 상태: `deployed`.
- ECS: 1 vCPU / 2 GiB, healthy 태스크 2개, 서울 리전 2a·2b 배치.
- RDS: 초기 Single-AZ에서 실제 Multi-AZ로 변경 완료.
- 자동 확장: 최소 2·최대 4, CPU 목표 60% 정책 등록 확인.
- 공개 HTTP 건강 검사 통과. 회원가입·로그인 후 같은 세션으로 서로 다른 앱 인스턴스 2개 접근 성공.
- 게시글 저장 후 조회 확인. 어댑터 배포 소요 662.196초, 이 중 DB 설정 단계 493.659초.

이번 실행은 `use_ai=false`로 선택 설계의 실제 배포 연결을 분리 검증했다. Claude 판단은 앞선
실측 결과를 참조한다. 실제 배포 규모는 medium만 검증했으며 small/large는 SDK 대역 테스트다.
이번 실행에서 부하에 의한 자동 확장·축소를 다시 검증하지 않았다. 실행 주체는 사용자 AWS
프로필이므로 생성된 최소 권한 정책만으로 배포 가능한지도 별도 검증이 필요하다.

### 중지 경로에서 발견한 제한

공개 경로의 HTTP 403 차단은 확인했지만, 중지 API는 ECS 서비스 삭제 완료를 기다리는
120초 제한 내 완료하지 못하고 HTTP 502를 반환했다. 별도 실험 정리 절차로 서비스와 기반 스택 삭제를 진행했다.
이를 정상 중지 API 성공으로 계산하지 않는다. ECS 제어 영역의 삭제 상태 수렴을 기다리도록
어댑터 제한을 600초, 엔진 DELETE 제한을 630초로 늘렸다. 이 보완은 자동 테스트까지 검증하며,
변경 후 실제 AWS 중지 API 재검증은 하지 않았다.

### 최종 정리

실험 총 실행 시간은 1,417초였다. 기반 스택 `DELETE_COMPLETE` 이후 독립 조회로 ECS 클러스터,
활성 task definition, ECR, 로그 그룹, RDS 인스턴스·스냅샷·자동 백업, ALB, VPC, Secret,
스택 IAM 역할, 자동 확장 대상·알람이 모두 남지 않았음을 확인했다. 이번 실행에서 생성된
ECS 자동 확장 서비스 연결 역할도 삭제 `SUCCEEDED`를 확인했다.

원시 결과의 `completed=true`는 배포·앱 검증 성공을 뜻하며 중지 API 성공을 뜻하지 않는다.
중지 API는 502였고, 후속 정리에서 자동 확장 삭제 요청 두 건의 오류가 기록됐다.
대상 재삭제는 `ObjectNotFoundException`이었으며 최종 독립 조회에서 대상·정책 알람 잔존은 없었다.
원시 증거는 `.data/experiments/2026-10-09/plan-deployment/`에 보관한다.
사용자가 예산 증액을 허용했지만 추가 실험은 실행하지 않았다. 확정 청구액은 집계 대기다.
