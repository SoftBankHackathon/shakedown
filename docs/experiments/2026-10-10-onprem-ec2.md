# EC2 as an on-premises Docker host — 2026-10-10

## Result

The existing local Compose runtime ran successfully on a disposable Amazon Linux
2023 EC2 host (t3.medium, encrypted 24 GiB root EBS). It did not use ECS or RDS.
Source: `85c12a53b5a23ffc535ca0aeb04f39ba4aefc8b2`.
GCP/Azure were outside this experiment's scope.

The existing VPC's Internet Gateway and active `0.0.0.0/0` route were reused,
with an auto-assigned public IPv4 address. The test app's TCP 18080 ingress was
restricted to the experiment client's `/32`. No SSH, database or control-API
ports were opened. Administration used an experiment-owned SSM instance role.
The existing shared VPC, subnet, route table and IGW were not modified.

A request from the developer's machine to the EC2 public address returned HTTP
200 and `{language: "node", database: true, count: 2}` before and after host
reboot/manual startup. No Cloudflare Tunnel or load balancer was involved.
This was a disposable HTTP probe without real user data, not HTTPS validation.

## Observed checks

- Local adapter unit tests: 12 passed, 0 failed on the EC2 host.
- Five real container combinations passed: Node without DB, Node with PostgreSQL
  split bindings, Node with DATABASE_URL, Python without DB, Python with PostgreSQL.
  PostgreSQL initialization ran twice in each DB case to check idempotence.
- Official MySQL 8.4 and MongoDB 8.0 images: real driver read/write, database restart
  persistence, special-character credentials and wrong-password rejection passed.
  The Mongo app account's admin command was denied.
- A separate PostgreSQL probe retained two records across app restart, then actual
  EC2 reboot (different Linux boot ID) and manual `docker compose up`.
- Control API health returned 200 on loopback; Origin and foreign Host requests
  returned 403. Listener inspection showed port 9101 on `127.0.0.1` only and
  app port 18080 on `0.0.0.0`. Database ports were not published.
- Node v22.23.2, Docker 25.0.14, Docker Compose v5.6.0.

## Gaps found

**Host reboot does not automatically restart the application or database.**
The generated Compose services have no restart policy; running services after
reboot were `[]`. Manual startup restored service and retained data. Automatic
startup, dependency/readiness handling and application DB reconnect behavior
need a separate implementation and test before unattended operation is claimed.

**The product's deployment path is still Tunnel-dependent.** `DockerRuntime.deploy`
starts cloudflared and requires public Tunnel health before returning ready.
For this experiment, the existing `composeSpec` output was used with the tunnel
removed and an app port added. That demonstrates runtime/network portability,
not a completed direct-IP/on-prem target selection feature. POST deployment through
the engine/Target API, offline networks, VPN/Direct Connect, public DNS/TLS,
HA, host-loss recovery and all language drivers were not verified.

An IGW is suitable for this EC2 public-internet experiment. It is not itself a
connection from a real corporate LAN to a private VPC.

## Harness and reproduction

Use only an explicitly disposable Linux host with Docker Compose and Node >=22.
Run from the repository root:

```sh
node infra/local/smoke-runtime.mjs
node infra/local/smoke-databases.mjs
node infra/local/experiments/onprem-reboot.mjs prepare /absolute/private-test-dir
# Reboot this disposable host, then:
node infra/local/experiments/onprem-reboot.mjs verify /absolute/private-test-dir
node infra/local/experiments/onprem-reboot.mjs cleanup /absolute/private-test-dir
```

The reboot harness binds the app to loopback by default. In this experiment only,
the generated private Compose file was changed to `0.0.0.0:18080:3000` after the
source-IP security-group restriction was in place. A direct public probe was then
run from the allowed client. Do not publish the unauthenticated control API.

Initial bootstrap stopped because the experiment's checksum parser did not account
for the `*filename` form in Docker's checksum manifest. The parser was corrected,
the checksum passed, and installation resumed via SSM. This was an experiment
setup error, not a product runtime failure; pristine unattended bootstrap was
not claimed. The existing smoke scripts' JSON scope labels mean those scripts
make no AWS API calls themselves; here they were executed on an actual EC2 host.
The reboot result's loopback label describes the harness default; this run used
the restricted public-port override described above.
