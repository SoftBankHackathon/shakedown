# AWS 통합 실험 — 2026-10-09

> 아래는 연결 구현 이전 실험의 기록이다. 이후 선택 설계→실제 배포 연결과 medium 실측을 완료했다. 최신 결과는 [선택 구성 배포 검증](2026-10-09-plan-deployment-connection.md)을 참조한다.

승인 예산은 앞선 실험을 포함해 총 3 USD이며 서울 리전을 사용했다.
이 기록은 기존 AWS 어댑터의 실제 배포와 별도 실험용 다중 AZ·자동 확장·RDS 검증이다.
**선택한 아키텍처 설계안을 제품 배포에 적용하는 기능은 아직 구현되지 않았다.**
배포 API는 `architecture_plan_id`를 받지 않고, 기존 어댑터는 0.5 vCPU/1 GiB와 최대 2개 태스크 계약을 사용한다.
실험 스크립트에서만 RDS Multi-AZ 및 최대 4개 태스크 자동 확장을 구성했다.

## 실측에서 발견한 배포 결함

기존 `AwsProvider.initialize()`는 실제 RDS 스키마 초기화에 성공했으나
`AwsProvider.deploy()`의 ECS CreateService는 실패했다. AWS CloudTrail 오류는
`The target group ... does not have an associated load balancer`였다.
초기 ALB listener가 고정 403만 반환하고, 건강 확인 뒤에야 대상 그룹으로
전달하게 되어 있어 ECS가 요구하는 대상 그룹과 ALB 연결이 없었다.

수정: listener의 기본 전달은 유지하고 모든 IPv4/IPv6 소스에 적용되는
우선순위 1 규칙으로 403 차단/전달을 전환한다. 기존 스택은 유지보수 중
인입을 막고 규칙·권한을 추가한 다음 `GateRuleArn`을 포함한 설정을 재생성해야 한다.
기존 팀 스택에는 이 변경을 적용하지 않았다.

신규 실험 스택에서 실제 ALB 연결과 HTTP 403을 동시에 확인했다.
자동 테스트에는 ECS CreateService 시 연결이 없으면 실패하는 조건과
서비스 생성 중 트래픽 차단, 건강 확인 후 개방 및 중지 전 차단 검증을 포함했다.
AWS 테스트 16개 및 엔진 전체 테스트 195개가 통과했다.

## 추가 발견: 기동 유예시간

앱 JVM 프로세스가 기동 완료까지 약 41초 걸렸고, ECS 서비스의 기존 건강 검사
유예시간은 30초였다. ECS 이벤트에 상태 불량으로 태스크 2개를 교체한 기록이
남았으며 앱 로그에는 정상 기동이 확인됐다. 유예시간을 120초로 늘렸다.
실행 중 설정 변경 후 세션·저장 검사가 통과했지만, 재배포 중 일시적으로 늘어난
태스크를 자동 확장으로 오인하지 않도록 측정을 중단하고 수정된 코드로 재실행했다.
최종 자동 확장 판정은 실제 desiredCount 증가와 단일 배포 상태도 요구한다.

## 실행 조건

- 알려진 `samples/kty-board` 소스로 AMD64 이미지를 빌드해 ECR digest를 고정했다.
- ALB 접근은 실험 PC IPv4 /32로 제한했고 DB는 외부 비공개·암호화·앱 보안 그룹만 접근하도록 구성했다.
- RDS PostgreSQL 17.6 / db.t3.micro / 20 GiB gp3 / Multi-AZ, NAT 없음.
- 앱은 실제 AwsProvider를 통해 생성한다. 세션은 JDBC, ALB stickiness는 비활성화한다.
- CPU target tracking의 1% 기준으로 확장을 유도하고 50%로 올려 축소를 관찰한다. 운영 정책 추천값이 아니다.
- DB 강제 failover 이후 AZ 전환, 기존 글 보존, 같은 로그인 세션으로 추가 쓰기를 확인한다.
- 전체 시험 제한 1시간, 정리 별도. DB·ECR·로그는 실험에서만 삭제 정책을 사용한다.

## 실행 결과

| 항목 | 관측 결과 |
| --- | --- |
| 실제 AWS Provider | RDS 스키마 초기화 및 앱 배포 성공 |
| 앱 다중 AZ | 2a·2b에 각각 배치, 태스크 2개와 ALB 정상 대상 2개 확인 |
| JDBC 세션 | 같은 쿠키로 서로 다른 인스턴스에서 로그인 상태 유지 |
| DB 저장 | 글 작성 후 API 조회로 저장 내용 확인 |
| 자동 확장 | 목표·실행 태스크 2→4, 96.53초에 정상 대상 3개 확인 |
| RDS 장애 전환 | 2a→2b, 71.57초에 DB 읽기와 기존 세션 추가 쓰기 복구 |
| 장애 이후 앱 | 목표·실행·정상 대상 모두 4개, pending 0 확인 |
| 자동 축소 | 최초 16분 관측에서 미확인; 성공 판정하지 않음 |

확장은 Application Auto Scaling의 CPU 정책 활동 기록으로도 확인한다.
96.53초는 정상 대상이 3개 이상인 조건을 처음 관측한 시간이며 네 번째의 정상화
시간을 뜻하지 않는다. 장애 복구 시간은 재부팅 API 호출부터 AZ 변경과 데이터 조회를
함께 확인한 경과시간이다. 실패한 폴링 1회와 일시적인 정상 대상 0개를 관측했다.
5초 간격 폴링·API 지연·HTTP timeout이 포함되므로 정확한 무응답 시간은 아니다.
다중 AZ DB가 무중단이라는 근거가 아니며, 보존·복구를 확인한 결과다.

축소용 CPU target은 50%, 실제 생성된 CloudWatch Low alarm은 CPU <45%를
60초×15개 기간으로 평가했다. 기동 중 높았던 CPU 값과 이후 낮아진 지표를 확인했지만,
초기 16분 관측 안에 축소 활동은 발생하지 않았다. 추가 관측 시도 시점에는 이미
정리 단계에서 정책과 서비스 삭제가 시작되어 유효한 재검증이 되지 않았다.
정책 재생성 시도도 서비스 상태 확인에서 중단됐고 추가 변경은 수행하지 않았다.
따라서 자동 축소는 미확인으로 남긴다. 집계 지연을 포함한 정확한 원인은 확정하지 않는다.
재현 스크립트는 관측을 최대 20분으로 늘렸으나 이 확대 구간을 성공 검증한 것은 아니다.

제품의 계획 선택→배포 연결 또한 미구현으로 남는다. 이 실험은 기존 Provider를 직접
호출했으며 웹 버튼→엔진→AWS 어댑터 전체 경로의 종단간 실측을 대신하지 않는다.

## 비용과 정리

기존 팀 스택은 변경하지 않았다. 첫 실패 스택은 DELETE_COMPLETE를 확인했다.
첫 스택에서는 서비스 생성 자체가 실패했기 때문에 정리 과정의 서비스 삭제 호출도
존재하지 않는 서비스 오류를 남겼지만, 스택 삭제와 잔여 리소스 확인으로 정리를 판정한다.
재현 스크립트는 서비스가 실제 ACTIVE인 경우에만 삭제하도록 보완했다.

재검증 스택도 DELETE_COMPLETE를 확인했다. 두 스택의 생성부터 삭제 완료까지
수명은 각각 31.54분, 50.87분이었다. ECS 클러스터, ECR 저장소, 로그, RDS,
스냅샷과 자동 백업, ALB, VPC, Secrets Manager 비밀정보, 스택 IAM 역할,
확장 대상 및 알람의 잔여 목록은 모두 비었다. 이번에 처음 생성된 ECS 자동 확장용
service-linked role도 삭제 상태 SUCCEEDED를 확인했다.

재검증 정리에서는 관측 연장을 위해 감독 프로세스를 일시 정지한 동안 진행 중이던
stop-task 호출의 timeout이 기록됐다. 이후 정리를 재개했으며, 위 독립 리소스 조회와
CloudFormation 삭제 완료로 실제 정리를 확인했다. cleanup_errors가 없었다고 주장하지 않는다.

### 비용 추산의 한계

확정 청구액은 집계 대기다. 서울 공개 단가 기준 0.5 vCPU/1 GiB 태스크는
시간당 $0.02839, db.t3.micro Multi-AZ는 $0.056, ALB 기본 시간 요금은 $0.0225,
공인 IPv4는 개당 $0.005다.

ALB 1개·공인 IPv4 12개가 유지됐다고 과대 가정한 기본 시간 요금 계산은 약 $0.7312다.
실제 사용량보다 큰 가정이지만 스토리지·LCU·DB 버스트 크레딧·로그·전송·세금은
별도이므로 청구 상한이나 확정 청구액은 아니다. 앞선 단일 태스크 실험 비용도 별도이며
전체 승인 예산은 3달러였다. 시험 자원은 모두 제거되어 과금 지속을 차단했다.
